## Cómo reproducir las comprobaciones

Desde una consola del runtime elegido, con Pester 5.8.0 y PSScriptAnalyzer 1.25.0
previamente instalados, usar el
[runner local](<C:/Users/FMS/Desktop/BEDROCK/LOCAL REPOS/atlas-pc-support/tests/Invoke-LocalChecks.ps1>).

```powershell
rtk proxy pwsh -NoProfile -STA -File ./tests/Invoke-LocalChecks.ps1
rtk proxy powershell -NoProfile -STA -ExecutionPolicy RemoteSigned -File ./tests/Invoke-LocalChecks.ps1
```

El comando de 5.1 debe ejecutarse en una consola nativa o con su `PSModulePath`
correcto. En este host una invocación heredaba módulos 7.0 antes de los módulos
nativos 3.1 y no encontraba `Get-FileHash`. Para la comprobación se antepuso
`$PSHOME/Modules` únicamente en ese proceso; no se cambió ninguna variable
persistente ni se instaló un reemplazo del comando.

Las fuentes Unicode se cargan desde copias UTF-8 con BOM para las pruebas 5.1.
Esto reproduce un contexto de carga correcto, sin reescribir los originales ni
afirmar que dot-source de cualquier archivo UTF-8 sin BOM funcione en 5.1.

Cada ejecución guarda `summary.json`, `analyzer.json` y `pester.xml` en una carpeta
temporal propia. La carpeta de build incluye espacios para ejercitar ese caso.
El runner no instala módulos ni ejecuta descargas de la herramienta. El CI puede
obtener los módulos de pruebas de PowerShell Gallery, con versiones fijas.

Las pruebas afirman el comportamiento seguro esperado y **deben fallar con el
código actual**. No son pruebas verdes del comportamiento defectuoso. Se usa texto
ficticio con extensión MSI; creación de procesos, red y cuentas tienen stubs que
bloquean la operación real y mocks que registran las llamadas. Se extraen las
funciones/ramas necesarias sin iniciar sus menús completos.

El CI básico mantiene seleccionadas las pruebas de bibliotecas y WPF. Al resolver
cada caso, su prueba se integra en el grupo de regresión obligatorio. Hasta entonces,
el aviso de la comprobación básica recuerda que verde no equivale a autorizar un release.
La suite no sustituye las pruebas adicionales de BitLocker, rollback y recuperación.

## Restricciones operativas durante la estabilización

- BitLocker: probar activación, recuperación, suspensión y descifrado en VMs con
  snapshot/vTPM y volúmenes de prueba; no usar un disco de cliente como banco de pruebas.
- Cuentas: crear escenarios de último administrador en VM; en el host solo operaciones simuladas.
- Instaladores: usar fixtures y mocks hasta que rechazo de firma/hash esté cubierto;
  después comprobar paquetes legítimos en VM.
- DNS, servicios, Hosts y spooler: pruebas posteriores con snapshots y reversión;
  no aplicar “optimización general” para preparar el entorno de desarrollo.
- Copias: usar archivos de prueba y destinos temporales antes de validar datos reales.

Son restricciones del procedimiento de trabajo de esta etapa. Esta entrega no
introduce bloqueos silenciosos en las tarjetas existentes ni cambia sus promesas
de compatibilidad sin la implementación correspondiente.

## Defender y enlaces de PC Support

Se conserva el contenido funcional de `get.ps1`, launcher, onboarding, herramientas,
Worker y manifiestos/hashes de distribución. No se cambian dominios, redirecciones,
política de caché ni la forma de arrancar el panel publicado durante esta fase.

Las pruebas no añaden exclusiones, desactivación de Defender/AMSI, comandos
codificados, ofuscación ni ejecución de contenido descargado. La política
`RemoteSigned` de las invocaciones de prueba afecta solo al proceso y no sustituye
la protección antivirus ni una firma de publicación. Microsoft distingue esos
alcances en [Execution Policies](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-7.5).

Si aparece una detección durante una fase posterior, conservar nombre de detección,
archivo/URL exactos, SHA-256, versión del motor y momento; confirmar primero su causa.
Un bloqueo de script, reputación SmartScreen, antivirus y política corporativa no son
el mismo diagnóstico. Para un falso positivo confirmado, usar el canal oficial
correspondiente; no cambiar dominios ni ofuscar el código para evitar el análisis.
Microsoft documenta la identificación de la fuente y el envío a revisión en
[gestión de falsos positivos](https://learn.microsoft.com/en-us/defender-endpoint/defender-endpoint-false-positives-negatives).
No se ha enviado contenido a terceros en esta fase.

Conservar artefactos no constituye una garantía de ausencia de futuras detecciones.
La firma y publicación coherente se trabajarán en A01/A06; la reputación externa no
se puede certificar mediante estos tests locales.
